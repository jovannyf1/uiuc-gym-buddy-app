# Project brief for future chats

This GitHub repository is the source of truth for **UIUC Gym Buddy App**. The student's goal is for a UIUC student to find another student free to go to the gym at the same time, agree on an accessible time and place, and work out together. Success means actual meetups, not just profiles or downloads.

Keep the product focused on gym buddies. Do not add gym busyness tracking or GPS location sharing. Students can manually enter weekly free times, upload `.ics` exports from Google/Outlook/Apple Calendar, or upload a screenshot for AI interpretation. All imported times must be reviewed before becoming recurring availability. Matching uses shared free windows, gym activity and location preferences; invitations have a specific date and accept/decline/cancel actions. Opt-in working-out-now presence, private chat, blocking, and reporting are also in scope. A native SwiftUI iPhone app is in `ios/` and shares the server API with the installable web app.

Read `README.md` before changing the app. Node.js 24+ is required. Run `npm ci`, `npm --prefix client ci`, `npm test`, and `npm run build`. The API is in `server/`; the React UI is in `client/`. Do not commit `.env`, `data/`, uploaded schedules, screenshots, or API keys. Screenshot interpretation uses a server-side `OPENAI_API_KEY`; the browser never receives the key.

Current limits: email/password sign-in accepts any address and lets a new user enter immediately; email verification is optional but needed for password reset and does not establish UIUC enrollment. The public email flow needs `EMAIL_FROM`, `PUBLIC_APP_URL`, and SMTP or Resend delivery; password reset uses that same provider. NetID sign-in is deferred and its public routes are disabled. Local development uses SQLite; the Vercel website and API use Supabase Postgres when `SUPABASE_DATABASE_URL` is set. Legacy pilot endpoints are development-only and are not a production account path. Calendar imports are one-time previews, not live sync; the AI screenshot path has automated tests but needs a configured API key for a live call. Reports are stored but have no human review workflow. The iOS source is included, but a physical device build needs Xcode, signing, and an API URL. Real mailbox testing, student testing, accessibility review, and a privacy/moderation plan remain before a wider campus launch.

An account reserves its lowercase `@username` and normalized email on creation, including while its email is unverified. The username is separate from the full name and is editable; existing accounts receive a starter `member<ID>` username.

When the student asks for changes in a new chat, work from this repository, run relevant checks, and put completed work back on GitHub. Avoid separate numbered local deliverables; give the GitHub link or commit/PR as the result.

For each user-facing change, state its expected visible result before checking it, add or update a meaningful repeatable check when useful, and update [`docs/VERIFICATION.md`](docs/VERIFICATION.md) with what was actually observed. Distinguish local tests, simulated email, hosted tests, and intended-user trials. Recheck the public address after deployment and leave any unavailable check marked untested.
